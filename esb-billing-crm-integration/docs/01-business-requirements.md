# 1. Бизнес-требования

## 1.1 Цель

Сократить ошибки и время при смене тарифного плана абонента: оператор меняет тариф только в CRM, а биллинг применяет изменение автоматически через ESB.

**Метрики успеха**

| Метрика | Сейчас | Цель |
| --- | --- | --- |
| Время смены тарифа оператором | ~4 мин (две системы) | ≤ 1 мин |
| Доля расхождений тарифа CRM ↔ биллинг | ~3% обращений | < 0,1% |
| Жалобы «списали по старому тарифу» | ~120 в месяц | снижение на 90% |

*Цифры условные, приведены для примера постановки цели.*

## 1.2 Заинтересованные стороны

| Роль | Интерес |
| --- | --- |
| Оператор контакт-центра | Одна система, быстрый результат, понятные ошибки |
| Абонент | Тариф меняется сразу, приходит SMS-подтверждение |
| Владелец продукта CRM | Меньше ручных операций, меньше жалоб |
| Команда биллинга | Корректные запросы, нет дублей, нагрузка в пределах SLA |
| Команда ESB | Единый формат, переиспользуемый сервис |
| Отдел отчётности | Событие о смене тарифа попадает в DWH |

## 1.3 Границы

**Входит:** смена тарифа действующего абонента (физлицо, постоплата и предоплата), проверка доступности тарифа, уведомление абонента, запись события.

**Не входит:** подключение нового абонента, корпоративные договоры, смена тарифа через мобильное приложение (будет второй этап и сможет переиспользовать тот же сервис ESB).

## 1.4 Бизнес-требования

| ID | Требование | Приоритет (MoSCoW) |
| --- | --- | --- |
| BR-01 | Оператор меняет тариф только в CRM, без входа в биллинг | Must |
| BR-02 | Перед сменой CRM показывает только тарифы, доступные абоненту (регион, тип оплаты, статус) | Must |
| BR-03 | Если на балансе не хватает средств на абонплату нового тарифа, смена не выполняется, оператор видит причину | Must |
| BR-04 | Смена применяется сразу или с 1-го числа следующего месяца, по выбору абонента | Should |
| BR-05 | Абонент получает SMS о смене тарифа | Should |
| BR-06 | Повторное нажатие или сбой сети не создают двойную смену тарифа | Must |
| BR-07 | Каждая смена тарифа фиксируется: кто, когда, со старого на новый, канал | Must |
| BR-08 | Событие о смене доступно отчётности (DWH) | Could |

## 1.5 Use Case: «Сменить тарифный план абонента»

| Поле | Описание |
| --- | --- |
| **ID** | UC-01 |
| **Основной актор** | Оператор контакт-центра |
| **Вспомогательные** | Биллинг, Сервис уведомлений |
| **Предусловия** | Оператор авторизован в CRM; абонент идентифицирован; абонент в статусе «Активен» |
| **Триггер** | Абонент просит сменить тариф |
| **Постусловия (успех)** | В биллинге новый тариф; в CRM обновлена карточка; абоненту отправлено SMS; событие записано |

**Основной сценарий**

1. Оператор открывает карточку абонента в CRM и выбирает «Сменить тариф».
2. CRM запрашивает у ESB список доступных тарифов для абонента.
3. Оператор выбирает тариф и дату применения (сейчас / с 1-го числа).
4. CRM отправляет запрос на смену тарифа в ESB.
5. ESB проверяет запрос, преобразует его и вызывает биллинг.
6. Биллинг проверяет баланс, меняет тариф и возвращает результат.
7. ESB возвращает CRM результат и публикует событие `tariff.changed`.
8. CRM показывает оператору «Тариф изменён» и обновляет карточку.
9. Сервис уведомлений отправляет абоненту SMS.

**Альтернативные сценарии**

- **5a. Запрос с тем же `requestId` уже обработан** — ESB возвращает сохранённый результат, повторно биллинг не вызывается (BR-06).
- **6a. Недостаточно средств** — биллинг отказывает, оператор видит «Недостаточно средств: нужно N ₸», тариф не меняется (BR-03).
- **6b. Тариф недоступен абоненту** — отказ с кодом `TARIFF_NOT_AVAILABLE`.
- **6c. Биллинг не ответил за 10 секунд** — ESB возвращает `503`, оператор видит «Сервис временно недоступен, повторите позже». Повтор с тем же `requestId` безопасен.
- **9a. SMS не доставлено** — смена тарифа не откатывается, ошибка уходит в лог сервиса уведомлений.
